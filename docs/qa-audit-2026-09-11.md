# QA audit: coverage, mutation effectiveness and black-box resilience

Audited 2026-09-11 at `760f4b0` (branch `qa/determinstic-guardrail`), Java 21.0.8 / Spring Boot 3.5.16, PostgreSQL 17.6, local ARM64 macOS Docker. The audit changed no repository file: coverage was attached on the command line, the widened mutation configuration ran in an exported copy of `HEAD`, and black-box probes ran against a separate Compose project (`wallet-ledger-qa`, port 18080, own volumes) built from `HEAD` with the repository Dockerfile and removed afterwards. The probe harness and derived Compose file are not part of the repository. Timings are local observations, not targets.

## Summary

| Measure | Result |
| --- | --- |
| Gate: `clean verify -Pmutation`, 55 s | 27 unit + 186 integration cases, zero failures/errors/skips; Spotless and packaging passed |
| PIT as configured (6 classes, 47 lines) | 26/26 killed |
| PIT widened to every application class, `*Test` + `*IT` as killers, 196 s | 307 mutants: 233 killed (76%), 32 survived, 42 without coverage; test strength 88% |
| JaCoCo (unit + integration) | Line 816/900 (90.7%), branch 112/164 (68.3%), method 165/190 |
| Black-box checks on the isolated stack | 176 passed, 3 failed, 11 observations |
| Emitted rejection codes asserted by name | 12 of 35 in the Java suite; 16 more only by the black-box run; 7 nowhere |

**Money movement held everywhere it was probed.** Over real HTTP: exactly 50 of 100 concurrent debits of 10 against 500 succeed and the wallet ends at balance 0, sequence 51 with 51 entries summing to 0; 50 identical requests post once; 20 concurrent provisions of one player yield one success and 19 `PLAYER_EXISTS`; 40 opposing transfers conserve the pair's total; 10 concurrent refunds reverse once. Killing the application with 39 credits in flight left no unfinished idempotency reservation, every key replayed to exactly one posting, receipts returned before the kill replayed identically, and `audit_ledger_integrity()` reported no findings afterwards.

**Three product findings**, all from failure injection: database unavailable returns a framework 500 instead of the documented 503 (F-01); one malformed Kafka record stalls projection for every wallet (F-02); an oversized integer in an event is narrowed and accepted, poisoning that wallet's projection (F-03).

**The automated suite would miss some regressions the brief cares about**: reversing a debit and every missing-player 404 never execute in `./mvnw verify`, and the concurrent-refund test cannot detect removal of its advisory lock (F-04 to F-08).

## Mutation effectiveness

The configured gate is strong for what it targets, and it targets 47 of 900 lines. Widened, the service-wide score is 76%. The 42 uncovered mutants match the coverage misses above. Of the 32 survivors, the ones that matter:

| Class | Killed / survived / uncovered | Surviving mutants |
| --- | ---: | --- |
| `WalletService` | 74 / 9 / 5 | Removing `lockBusiness` in `refund`; removing `lockReference`, `required` and `metadata` in `transfer` and `refund`; the `delta > 0` boundary in `refund` |
| `RewardService` | 24 / 8 / 3 | Removing `requirePlayer` from all four entry points; removing every `validateText` call in `completion` |
| `RewardRepository` | 13 / 2 / 0 | `completionClaimed` and `promotionClaimed` forced to `false` |
| `BalanceProjection` | 6 / 3 / 0 | Zero-sequence and zero-balance boundaries; negating the already-consumed check |
| `SecurityConfiguration` | 9 / 5 / 2 | JWT authority-converter wiring; unassessed because `ConfiguredJwtHttpIT` was excluded from the killer set |
| `OutboxRelay` | 5 / 3 / 6 | Delivery and failure counters, interrupt handling |
| `CommandExecutor` | 30 / 0 / 10 | Nothing survives in covered code; the retry loop never runs |

Survivors are not bugs. In every case examined, removing a service-level guard leaves a database constraint or later money rule that still rejects the request, with a different code or a 5xx, and the tests count statuses rather than codes. The 12 hand-written SQL mutants in `LedgerSqlMutationIT` all still die. By first kill, `RewardServiceIT` (48), `HttpApiIT` (45), `HttpAuthorizationIT` (35) and `WalletLedgerIT` (28) do most of the work.

## Black-box results

Verified over HTTP against the isolated stack, with database state checked after each step:

- **Validation.** Amounts `0`, `-1`, `1.5`, `"10"`, `2^63`, `null`, `1e2`, `true` and a missing amount return 400 `INVALID_INPUT`; blank, oversized or missing reason/source/reference and key do the same; none consumes the idempotency key, and the same key then succeeds with a valid body. Unknown fields, malformed JSON and non-UUID paths return 400.
- **Idempotency.** Replay after a later debit returns the original receipt with its stale `balanceAfter`; the same key with changed content, on another endpoint, or from another caller behaves as documented; a 404 rejection replays as the same 404.
- **Limits.** A credit of `Long.MAX_VALUE` is accepted; one more unit is 409 `BALANCE_LIMIT` with no state change; the JSON balance keeps full precision.
- **Transfers.** Fresh and replayed receipts contain exactly the ten allow-listed fields; self-transfer 400 `SELF_TRANSFER`; unknown recipient 404 with no debit; SERVICE and ADMIN callers 403; a client-supplied `senderId` is rejected before any key is reserved.
- **Refunds.** A debit reversal restores the balance and returns `originalTransactionId`; second refund 409 `ALREADY_REFUNDED`; refund of a refund or a transfer 409 `REFUND_NOT_SUPPORTED`; unaffordable credit reversal 409 `INSUFFICIENT_FUNDS` with no change.
- **History.** Page sizes 3/3/1 with a null final cursor, sequences 7…1 without gaps, running balances chain; `limit` 0/101/`abc`/−1 and `cursor` 0/`abc` return 400.
- **Rewards.** Daily, trusted and promotion claims credit the server-decided amount while client-supplied `amount` and `playerId` are rejected or ignored; foreign completion 403 `COMPLETION_NOT_OWNED`; wrong reward 409 `COMPLETION_REWARD_MISMATCH`; completion recording is idempotent per source reference and 409 when reused for another player.
- **Infrastructure.** Health reports `DOWN` (503) with PostgreSQL stopped and recovers; the key used during the outage succeeds afterwards; a request caught by a frozen database completed exactly once after unpause; the outbox drained to zero and the real listener's projection converged for every wallet with postings (270 events consumed, 270 outbox rows).
- **Rate limiting.** The 21st request in a window is 429 `RATE_LIMITED` as problem JSON with `Retry-After: 60`; a rate-limited mutation reserves no key; other callers and health probes are unaffected; with Redis paused, requests pass and `wallet.rate_limit.degraded` increments; limits resume when Redis returns.

Observations, intentional or documented but worth knowing: 405 and 415 responses carry code `INVALID_INPUT` and no `Allow` header; a debit may reuse a credit's `(source, reference)` because uniqueness is per operation; history rows omit refund origin and transfer counterparty; a request against a frozen database hangs indefinitely because no client-side JDBC socket timeout is configured.

## Findings

| # | Finding | Severity · category | Evidence |
| --- | --- | --- | --- |
| F-01 | Database unavailable returns HTTP 500 with Spring Boot's default error body, not the documented 503 problem response | high · product | Credit with PostgreSQL stopped: 500 after 5.1 s, no `code`, no `Retry-After`. Log: `CannotCreateTransactionException: Could not open JDBC Connection`. It is a `TransactionException`, not a `DataAccessException`, so `ApiProblems` never sees it |
| F-02 | One malformed Kafka record halts projection for every wallet | high · product | After producing `{"garbage":true}`, six freshly credited wallets across all partitions showed no projection movement in 25 s; the listener logs "Record in retry and not yet recovered" and seeks back on all three partitions once per second. `DefaultErrorHandler` has unlimited retry and one listener thread |
| F-03 | Oversized integers in events narrow silently and poison a projection | medium · product (consumer) | Event with `walletSequence` 999999 and `balanceAfter` 2⁶⁴+5 stored as sequence 999999, balance 5; the wallet's next real credit was ignored as stale. `JsonNode.longValue()` keeps the low 64 bits. Requires topic write access |
| F-04 | The concurrent-refund test cannot detect loss of the refund advisory lock | medium · test quality | Passes 5/5 runs without the lock, even with a widened race window. The racing refund drains the wallet, so the loser is rejected as `INSUFFICIENT_FUNDS` before reaching the lock, and the test only counts 409s. The same applies to `lockReference` in transfer and refund |
| F-05 | Reversing a debit is never executed by the automated suite | medium · test quality | `WalletService` refund credit branch uncovered; every test refunds a credit. The brief's "cancelled purchase" refund is exercised only by `scripts/demo.py`, which asserts nothing |
| F-06 | Missing-player handling is untested in automation | medium · test quality | 404 constructors uncovered; four `requirePlayer` removals survive. Black-box confirmed 404 `PLAYER_NOT_FOUND` on credit, debit, balance, history, transfer recipient and completion |
| F-07 | Status-only assertions let guard removals pass | medium · test quality | `completionClaimed`→false survives (second claim still 409, as `BUSINESS_REFERENCE_USED`); `promotionClaimed`→false survives (no test claims a promotion twice); the projection dedup negation survives (first delivery's effect never asserted); no test sends a balance-zero event |
| F-08 | Production paths never run under `./mvnw verify` | low · test quality | 429 branch, `ApiProblems` handlers, transient retry loop, real listener/relay beans, filter-level access-denied handler. All exercised only by the black-box run |
| F-09 | 405 and 415 lose their semantics | low · product | Mapped to `INVALID_INPUT`; `handleExceptionInternal` discards the `Allow` header Spring prepared |
| F-10 | No client-side deadline when the database freezes | low · operations | Request hung past 12 s with the container paused; server-side `statement_timeout`/`transaction_timeout` cannot fire on a frozen server. Money was safe: it completed once after unpause and the key replayed correctly |
| F-11 | The mutation gate measures 47 of 900 lines | low · process | Widened run is 76% in 196 s with the same plugin |

Suggested fixes, in plan order: handle `CannotCreateTransactionException` as 503 with `Retry-After` and `TransactionSystemException` as problem-JSON 500, with an integration test that pauses the database container (step 3); mark `IllegalArgumentException` not retryable, bound the back-off and recover to a quarantine table or dead-letter topic with an alert, tested with the real listener (step 4); use `canConvertToLong()` or a strict event DTO (step 4); assert rejection codes in race tests and add a debit-refund race, a debit-reversal case, a missing-player matrix, a duplicate promotion claim and a balance-zero event; widen `targetClasses` and `targetTests`, add JaCoCo with a branch threshold; set a JDBC `socketTimeout`.

## Recommended additions

1. Widen the PIT gate to the whole service with integration tests as killers (threshold 75%, raised as survivors are fixed) and add JaCoCo with a branch threshold.
2. Fault-injection integration tests using Testcontainers' `pauseContainerCmd`/`stopContainerCmd`, as `MessagingIT` already does for Kafka: 503 body, `Retry-After`, same-key recovery.
3. Real listener tests with `ledger.consumer.enabled=true`: valid, malformed, out-of-range and balance-zero events; a relay test with two instances competing for one lease.
4. Randomised concurrency: a few hundred random credit/debit/transfer/refund/claim operations with duplicated keys, checked against an in-memory oracle and `audit_ledger_integrity()`.
5. Property-based tests (jqwik) for `MoneyRules`, `DailyRewardPolicy` and `ProjectionPolicy`; an OpenAPI contract check in `HttpApiIT`; ArchUnit rules that only `WalletService` writes ledger tables.
6. Load outside the JVM (k6 or Gatling) followed by `scripts/audit-ledger.sql`; a weekly 20× loop of the race and deadline tests to surface flakiness; Trivy and dependency-check in the gate (PostgreSQL 17.6 is behind the 17.11 security release).

## Limits

Single machine, single-node containers; Kafka replication and a production identity provider were not exercised. `ConfiguredJwtHttpIT` was excluded from the widened PIT run because its static JWK server does not survive repeated in-process runs, so five `SecurityConfiguration` survivors are unassessed. Promotion exhaustion cannot be reached over HTTP with the two demo player identities; it is covered by `RewardRacesIT`. Four first-pass probe failures were harness bugs (unpinned references on replay, comparing wallets with no postings, a missing timeout argument, Compose restart ordering); their scenarios were rerun after fixes and the merged tally counts the reruns. Generated reports under `target/` are ephemeral; `git status` was clean when the audit ended.
