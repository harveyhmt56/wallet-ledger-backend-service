# Wallet ledger QA audit — 2026-09-14

The requested core wallet requirements are verified in the tested conditions. No authoritative balance corruption, duplicate posting, overdraft, or partial money update was found. **Production sign-off is withheld:** the database error contract and Kafka consumer still have reproducible defects. Passing tests and coverage do not prove correctness under every failure or production load.

The audit started from clean commit `f2a7e07` on `codex/QA-full-project-verify`. Changes since the memory baseline `e6472f7` were documentation only. This audit adds four integration cases and evidence; application code, SQL migrations, dependencies, and deployment configuration are unchanged.

## What protects the money

`WalletService` locks wallet rows before validating available funds and uses a consistent order for transfers. `MoneyRules` checks positivity, insufficient funds and overflow. `CommandExecutor` reserves the request key, executes the posting, and stores its receipt in one PostgreSQL transaction; business rejections use a savepoint. Posting includes journal, entries, wallet state and outbox. Deferred checks independently reject broken balance/sequence/entry relationships.

The new controlled race holds an actual debit of 80 from 100 **uncommitted**, then observes the competing command blocked by that exact PostgreSQL backend PID. After the first commits, the second returns `INSUFFICIENT_FUNDS`; balance is 20 with exactly one debit journal. This checks the actual ordering that a client start barrier alone cannot prove. PostgreSQL documents that `SELECT FOR UPDATE` waits and returns the updated row; Spring documents JDBC savepoints for `NESTED` transactions. [PostgreSQL 17 locking](https://www.postgresql.org/docs/17/explicit-locking.html), [Spring 6.2 propagation](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/tx-propagation.html).

It detected **52/52**. The scratch broader POM targets all application classes and `*Test`/`*IT`, with two workers and the same thresholds. `ConfiguredJwtHttpIT` is excluded only there because its fixture cannot be repeated in one JVM. Broader mutation line coverage is 859/886, a different scope/denominator from JaCoCo. PIT reports 290 `KILLED` outcomes out of 307 (94.5%); no timeout was counted as a kill. That outcome does not distinguish assertion failures from every other legitimate test failure. [PIT configuration](https://pitest.org/quickstart/maven/).

## Reproduced findings and remaining limits

**F-02 — Poison Kafka record stalls delivery [high, product/availability, high confidence].** With a single listener assigned partitions 0/1/2, valid controls on partitions 0 and 1 projected successfully. Malformed JSON at partition 0 offset 1 retried five times. Over the subsequent three-second observation, the later valid records at partition 0 offset 2 and partition 1 offset 1 were both unprocessed; committed offsets remained 1 on each partition. No claim is made about every deployment or every other partition. `MessagingConfiguration.consumerErrors()` configures unlimited attempts; `BalanceProjection` throws `IllegalArgumentException`, which is not a default fatal classification. Add bounded retry, durable quarantine with replay, and a regression requiring subsequent valid records to progress. Authoritative wallet reads bypass this projection. [Source](../src/main/java/com/example/walletledger/messaging/kafka/MessagingConfiguration.java), [Spring Kafka 3.3 recovery](https://docs.spring.io/spring-kafka/reference/3.3/kafka/annotation-error-handling.html).

**F-03 — Oversized event integers corrupt the projection [medium, product/data validation, high confidence].** The parser accepted sequence `27670116110564327423` and balance `18446744073709551616`, storing `Long.MAX_VALUE` and zero. A later genuine sequence-2/balance-70 event could not repair it. The authoritative wallet remained 70 at sequence 2 and the full ledger audit was clean. It also accepted schema versions `1.5`, `"1"`, `true`, and `4294967297`. Require exact field types/ranges before conversion, then reject/quarantine invalid events. The impact requires invalid input reaching the Kafka/projection boundary; the wallet HTTP amount parser already rejects such numbers. [Parser](../src/main/java/com/example/walletledger/messaging/kafka/BalanceProjection.java), [Java 21 BigInteger narrowing](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/math/BigInteger.html#longValue()).

**F-01 — Database transaction-start errors escape the structured response [medium, product/error contract, high confidence].** With a stable loopback endpoint, stopping the audit PostgreSQL container produced a generic HTTP 500 after 5.824 seconds, without a stable `code`. After restart, the failed debit had no reservation or money effect; the same key succeeded and replayed exactly, ending at balance 70/sequence 2 with two player entries, two outbox records and a clean full audit. The exception is `CannotCreateTransactionException`, outside the advice's `DataAccessException` handler. Add explicit classification for transaction-start dependency failures, preserving safe same-key retry guidance; distinguish unknown transaction failures from known transient failures. This is failure clarity/operability, not demonstrated lost money. Prior reports ranked it high; this audit ranks the reproduced consequence medium. [Advice](../src/main/java/com/example/walletledger/configuration/ApiProblems.java), [Spring 6.2.19 exception hierarchy](https://docs.spring.io/spring-framework/docs/6.2.19/javadoc-api/org/springframework/transaction/CannotCreateTransactionException.html).

**Database defense boundary [medium hardening gap, no demonstrated HTTP exploit].** Generic commit checks validate journal magnitude/currency/balance, but do not enforce CREDIT/DEBIT/TRANSFER account/sign semantics. Existing `LedgerIntegrityIT.severalValidPostingsUseFinalWalletStateAtDeferredCommit` commits a negative player delta under a helper header labelled CREDIT. Refund inverse shape is checked by the full audit, not the commit trigger. The application currently constructs the correct entries. Add operation-shape/inverse checks in a **new migration** if the database must independently reject a faulty future posting implementation. [V4](../src/main/resources/db/migration/V4__indexed_ledger_integrity.sql), [executable boundary](../src/test/java/com/example/walletledger/wallet/LedgerIntegrityIT.java).

**Lower-priority/source-confirmed observations.** History preserves explanatory fields but omits refund-origin and transfer-counterparty fields from its API representation; the permanent database relationships exist. Generic validation names no individual field. `ApiProblems` discards framework headers such as 405 `Allow` and classifies every handled `DataAccessException` as 503. These remain usability/error-classification work; no new runtime probe was run for 405/415. The JDBC URL has no socket read timeout, and the configured statement timeout is not a universal transaction/transport deadline; the existing deferred-COMMIT tests confirm the narrower boundary. A frozen-database test was not rerun here. [History/source](../src/main/java/com/example/walletledger/wallet/application/WalletService.java), [configuration](../src/main/resources/application.yml), [pgJDBC timeout options](https://jdbc.postgresql.org/documentation/use/).

The audit did not establish production capacity, multi-process host failure isolation (the new HTTP contexts share one JVM), Redis-enabled HTTP pressure behaviour, multi-broker durability, competing relay leases, live identity-provider behaviour, hosted CI execution, backup/restore, storage loss recovery, or a production migration pipeline. The 20k-history integration test ran; a new latency/capacity benchmark was not performed. Prior reports remain historical evidence only. Deployment patch/security assessment was not part of this money-correctness run.

## Audit errors, cleanup and worktree changes

The first F01 harness attempt reproduced the HTTP failure but its dynamic endpoint could not reconnect after container restart. Its recovery assertion timed out, so that attempt did **not** verify recovery. Its original source/XML are retained; the revised probe owns a PostgreSQL fixture with an explicitly allocated loopback host port and verifies unchanged bindings across restart. Its rerun passed in 23.929 seconds. Dynamic port remapping was suspected, but the original post-restart binding was not captured, so the initial cause remains unproven. No selected final scenario has an unresolved harness error. This is a harness correction, not an application fix. Characterization probes deliberately assert current defects and are kept outside the normal test suite; their passing result is evidence that a defect exists, not a product pass.

Final Docker inspection showed only the same four original Compose services, still up six days, and no remaining Testcontainers-labelled containers. No global cleanup was used. The initial worktree was clean. Final intended changes are the new HTTP test, one additional database test, this report/evidence, README test documentation and memory/verification notes. Existing tests and application behaviour are preserved. No remote push, publication, deployment or production data change was performed.
